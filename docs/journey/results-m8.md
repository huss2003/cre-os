## Summary of failures and fixes

1. **8.2b (HIGH):** an estimated (unconfirmed) budget is used as a hard "Rent ≤ budget" rule, which disqualifies Property C.
   - Fix in `src/modules/toolkit/comparison.ts` `loadRequirement`: only set `budgetMax` when the budget field status is `client_confirmed`.
2. **8.2a (MEDIUM):** a rule whose requirement value is not set returns `pass`.
   - Fix at `src/modules/toolkit/calc/rating.ts:158`: return `unknown` (or a distinct `not_applied`).
3. **8.11 (MEDIUM):** the proposal and decision summary are not client-ready.
   - The recommendation renders as JSON.
   - Advantages, shortcomings and occupancy costs are missing, because of the 25-line flatten.
   - Fix in `src/modules/toolkit/deliverables.ts`: `recommendationOf` plus per-kind sections. Also add advantages/disadvantages and a requirement summary in `deck.ts`.

## Retest 2026-11-11 — all fixed: 22 tests, 22 passed (`npx vitest run src/modules/toolkit tests/journey/m8-toolkit.test.ts`: 131/131)

- **8.2a:** `calc/rating.ts` — a rule with no requirement value now returns the new outcome `not_applied` (never `pass`, and it does not block eligibility). The compare page renders it as "– Not applied". The test now asserts `not_applied` (and `not pass`): with `unknown` every property would have become "unconfirmed" and nothing could be recommended.
- **8.2b:** `comparison.ts loadRequirement()` sets `budgetMax` only when `constraints.field_status.budget === "client_confirmed"`. Otherwise it sets `budgetEstimate`, and rating adds a soft disadvantage, "Over the estimated budget (unconfirmed) … not excluded", plus a verification item. C is now eligible, and the recommendation no longer says "excluded".
- **8.11:** `recommendationOf()` returns readable text (explanation, else the property name, never JSON). The proposal and the decision summary have proper sections: requirement summary, property details, commercial comparison, occupancy costs (monthly rent/CAM/total before other charges, CAM escalation, other charges "Not provided", refundable deposit separately, totals over the term, NPV), advantages, shortcomings, site-visit feedback, assumptions, missing information, recommendation and supporting evidence. The deck adds a requirement summary, an advantages/shortcomings slide and "Recommended: …". The corporate `template_asset` (purpose `proposal`) is applied and named in "Sources and versions". This is tested with a tagged WS1 template that the test deletes afterwards.
- **8.3/8.5 notes:** `leaseEconomics` now returns `monthly.totalBeforeOther` (rent + CAM), `camEscalation` ("none" when not entered) and `otherCharges` ("not provided" when unknown). These are shown on `/toolkit/lease`.
- **7.9 (added):** comparisons now load `meeting_property_feedback` (site visits linked to the requirement or its opportunities) into `outputs.siteVisitFeedback`. The feedback (comments, plus parking and pricing concerns) is shown on the compare page, in the proposal and in the deck, and it never changes eligibility. There is a new journey test for it.

No CRITICAL issues. Every rent, CAM, deposit, escalation, rent-free, TCO, managed, renewal and negotiation figure matched the independent decimal.js calculation.
