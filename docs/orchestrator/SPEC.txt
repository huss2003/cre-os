MODULE 9: ORCHESTRATOR

Master AI Development and Implementation Prompt

You are a senior software architect, workflow automation engineer, AI systems engineer and full-stack developer.

Your task is to build Module 9 – Orchestrator for the Pune Commercial Real Estate AI Operating System.

The Orchestrator is the central coordination engine responsible for managing schedules, dependencies, background jobs, automated workflows, reminders and communication between the system's modules.

It must ensure that the entire CRE operating system functions as one connected business application rather than a collection of independent modules.

The Orchestrator must understand which operations need to happen, when they should happen, which module should perform them, what information they require, what depends on their completion and what should happen if an operation fails.

It must not duplicate the business logic of individual modules. It must coordinate their existing services.

---

1. CORE OBJECTIVE

Build a central workflow orchestration system capable of:

1. Running scheduled source updates.
2. Running research and signal checks.
3. Triggering scoring recalculations.
4. Coordinating contact enrichment.
5. Managing meeting preparation.
6. Triggering post-call and post-meeting processing.
7. Generating daily plans.
8. Managing reminders and follow-ups.
9. Coordinating weekly reviews.
10. Managing background processing jobs.
11. Reassessing affected outputs when underlying information changes.
12. Respecting the user's calendar, travel requirements and daily capacity.
13. Prioritising urgent client work over routine research.
14. Routing tasks to the appropriate specialist module.
15. Retrying temporary failures without creating duplicate actions.
16. Tracking successful, delayed, failed and pending operations.
17. Managing research, enrichment, transcription and AI usage budgets.
18. Providing pause, resume and retry controls.
19. Maintaining a complete execution history.
20. Providing meaningful alerts instead of overwhelming users with notifications.

The system should operate in the background with minimal user intervention while maintaining human control over consequential actions.

2. ARCHITECTURAL PRINCIPLE

The Orchestrator is a workflow coordination layer, not another business database or AI assistant.

Use the following responsibilities:

- Module 1 owns business records.
- Module 2 owns research and signal detection.
- Module 3 owns scoring calculations.
- Module 4 owns contact enrichment.
- Module 5 owns outreach drafting and communication workflows.
- Module 7 owns meeting preparation and follow-through.
- Module 8 owns commercial analysis and validated calculations.
- Module 12 owns conversational interaction and natural-language task requests.
- Module 9 coordinates when these services execute and in what sequence.

Do not recreate these modules' functionality inside Module 9.

The Orchestrator should invoke existing backend services through well-defined APIs or internal service interfaces.

It must not directly bypass business rules, permissions or approval requirements.

6. WORKFLOW DEPENDENCY MANAGEMENT

The Orchestrator must understand that some tasks depend on other tasks.

For example:

A property comparison cannot be considered complete if the required property quotations are missing.

A meeting brief cannot be prepared accurately if the meeting attendees cannot be identified.

A scoring recalculation must use the latest available relevant information.

Example dependency chain: New CRE opportunity

1. Module 2 detects a signal.
2. Module 1 identifies the company.
3. Module 3 recalculates the lead priority.
4. Module 4 identifies missing stakeholders.
5. Module 12 can explain the opportunity.
6. Module 5 can prepare outreach when requested or configured.

The Orchestrator must track the completion of each step.

Dependency rules

- Use explicit dependencies.
- Identify missing prerequisites.
- Avoid unnecessary repeated processing.
- Allow independent tasks to execute in parallel.
- Do not assume that a previous result remains current after its inputs change.
- Reassess affected outputs when relevant information changes.
- Preserve the previous output and its version.

7. INTELLIGENT REASSESSMENT ENGINE

One of the most important functions of Module 9 is to identify which existing outputs have become outdated after a business record changes.

Implement a dependency-aware invalidation and recalculation system.

Example 1: New rent quotation

Event: A new rent quotation is uploaded.

Orchestrator actions:

1. Identify the affected property.
2. Identify requirements and opportunities linked to the property.
3. Identify existing commercial comparisons.
4. Identify proposals using the old quotation.
5. Trigger recalculation through Module 8.
6. Mark affected draft outputs as requiring refresh.
7. Warn the user if an approved or shared proposal contains outdated information.
8. Preserve the old quotation and calculations.

Example 2: Requirement area changes

Event: Client requirement changes from 25,000 SF to 30,000 SF.

Orchestrator actions:

1. Update the requirement through the authorised workflow.
2. Identify affected property comparisons.
3. Trigger new suitability assessments.
4. Recalculate relevant occupancy economics where inputs are affected.
5. Reassess requirement readiness.
6. Identify outdated proposals.
7. Notify the responsible user.

Example 3: Meeting cancelled

Event: Meeting is cancelled.

Orchestrator actions:

1. Update meeting status.
2. Cancel associated preparation reminders.
3. Cancel meeting-specific pending tasks where appropriate.
4. Preserve historical meeting information.
5. Notify the user if other commitments remain active.

Example 4: Contact changes employer

Event: A contact's employment changes.

Orchestrator actions:

1. Update or propose the employment-history change.
2. Preserve previous employment.
3. Review current contact-company relationships.
4. Identify affected stakeholder maps.
5. Flag any open relationship or opportunity associations requiring review.
6. Do not automatically move company opportunities to the new employer.

Example 5: Source outage

Event: A monitored source becomes unavailable.

Orchestrator actions:

1. Record the failure.
2. Identify the affected data source.
3. Display the last successful update.
4. Mark affected information as potentially stale.
5. Retry according to the configured policy.
6. Alert the user if the failure affects important decisions.

11. RETRY AND FAILURE MANAGEMENT

Implement a durable retry and recovery system.

11.1 Retry Rules

- Retry temporary network failures.
- Retry recoverable provider errors.
- Use exponential backoff with configurable limits.
- Do not endlessly retry permanent failures.
- Do not retry a consequential action blindly.
- Use idempotency keys for operations that may be repeated.
- Preserve successful earlier steps.
- Resume from the failed step where safe.

11.2 Partial Failure

Example:

A research workflow contains:

1. Company search.
2. News retrieval.
3. Contact enrichment.
4. Scoring recalculation.

If contact enrichment fails, the system should preserve the successful research and company matching results.

It should retry the failed enrichment step without repeating successful operations unnecessarily.

11.3 Failure Reporting

Every failure must explain:

- What failed.
- Which records are affected.
- Whether any previous steps succeeded.
- Whether information may be stale.
- Whether the system will retry.
- What the user needs to do.

11.4 Recovery Controls

Provide:

- Pause.
- Resume.
- Retry.
- Reconnect.
- Cancel.
- Export logs.
- View affected records.

Technical requirements

- Use a durable queue for background execution.
- Use a scheduler for recurring jobs.
- Use database-backed workflow state.
- Use idempotency keys.
- Use transactional event publishing where appropriate.
- Use retries with backoff.
- Support concurrency limits.
- Support job timeouts.
- Support dead-letter handling for repeatedly failing jobs.
- Use distributed locks where required.
- Maintain audit logs.
- Respect workspace isolation.
- Support cancellation and recovery.

Do not depend on a single in-memory process for important scheduled work.

A server restart must not silently erase pending jobs or scheduled workflows.

Event processing reliability

Use reliable event publishing and consumption patterns.

Where appropriate, implement a transactional outbox and idempotent consumers so a database update and its corresponding event are not lost or inconsistently processed.

Do not guarantee exactly-once execution across external systems. Instead, use durable processing, idempotency and reconciliation to achieve safe practical behaviour.
